# PRの安全な統合計画（実行には所有者の承認が必要）

PR #1基盤 → #2調査 → #3正規化 → #4数理仕様 → #5単一コア → #6反復 → #7可視化 → #8操作画面 → #9独立監査 → #10操作性 → 第12工程PR の順に継承する。開始時の各head/base/CIは ../verification/github-start.json。mainは初期コミット3e6a155で、作業ブランチの完成とmainへの統合は異なる。

1. 各PRをbaseとのdiffでレビューし、最新headのCI成功を確認する。公開設定と未解決事項を含め所有者が承認する。
2. 原則merge commitを用いる。squash/rebaseで既存の来歴が参照するコミットを失わせない。枝を削除する前に参照コミットが履歴から到達可能なことを確認する。
3. #1をmainへマージした後、#2のbaseをmainへ変更し差分とCIを再確認して承認・マージ。同じ手順を順番に行う。親ブランチの削除による自動base変更に依存しない。
4. コンフリクトを自動で片側採用しない。原CSV・正規化・規範仕様・PCGが変わる場合は独立監査を再実行する。
5. 全統合後に完全履歴でmainを新しくcheckoutし、npm ci / npm run check / 独立Python監査 / scripts/release/build.mjs / ブラウザE2Eを再実行する。
6. application Git IDが統合により変わった場合は実在するIDと実バイトを再照合する。既存のIDを固定して偽装しない。core版が変われば正式JSONも変わり得るため旧成果物と比較し理由を記録する。
7. 統合後manifestと出力来歴を新たに保存してから不要な作業ブランチの整理を検討する。履歴をforce pushで書き換えない。

PRをマージすることと一般公開の承認は別。mainへ統合しても自動公開を有効化しない。現在、こちらから既存PRのマージ・mainへの直接pushはしていない。
