# 第4工程：取得・正規化・品質検証の実装仕様

この工程はデータ処理基盤まで。シミュレーション、抽出、乱数、反復、ネットワーク描画、指標・スコア、AI補完、バックエンド、公開は実装しない。既存4画面は変更せず、ローダーをシミュレーションや分析画面へ接続しない。

## 固定入力とライセンス

大学保管v1・DOI `10.25405/data.ncl.17430548.v1`、ファイルID `34178859` のみを採用する。元CSVは254,165 bytes、SHA-256 `c2d7023215fb885070caf6603886bce10e965732e3cc2465111e9d73cad9ab9a`、MD5 `6f083ca81e9bc14c3bbd5806aecb62e8`。GitHubのLF版へ置き換えない。`contract.ts` と第3工程のmanifestを照合する。

`data:fetch` は指定URLから取得し、サイズ・両ハッシュを確認する。版付き公式APIでDOI・版・ファイルID・名前・サイズ・MD5・CC BY 4.0も確認し、成功してから保存する。不一致・HTTPエラー・タイムアウトは失敗として終了し、別の版を探して採用しない。既存原本がある場合は原本・取得メタデータ・ライセンス証拠を検証し、取得日時を維持する。取得の途中で保存に失敗した場合は残ったファイルを確認し、無条件に上書きしない。

Ellen Moss / Darren Evans (2022)、タイトル、版、DOI、CC BY 4.0へのリンク、変更内容、承認を意味しない旨を `data/README.md`・`source.json`・`provenance.json` に保持。元CSVは無変更、派生データには正規化・監査を行った旨を示す。取得時の公式API応答を保存してハッシュ検証する。メタデータに変動する項目があっても、固定CSVの版・ハッシュ検証を緩めない。

## 実行方法と責務

Node.js **24.12以上**（`.nvmrc` は24）、`npm ci` を使用する。NodeのネイティブTypeScript型除去を使うCLIと、Web Cryptoを使うブラウザ用ローダーを分離する。CSVパーサーは `csv-parse` **7.0.3**、ロックファイルで固定。パーサーは開発時CLIの依存であり、ブラウザ用公開エントリーからNode用モジュールを参照しない。

## 正規化の確定ルール

[normalization.md](normalization.md) の原名設計を実装。共通の `dataset_id`・`source_sha256`・`schema_version`・`transform_version` はイベントを囲むオブジェクトに1回置く。各イベントの出典はこのコンテナと `record_id` から追跡できる。イベント個別に同じ共通情報を複製しないことが設計案からの配置上の具体化。

CSVはUTF-8を厳密にデコードし、専用パーサーで引用符・カンマ・CRLFを扱う。7列のヘッダー順を固定し、余剰・不足列、空欄、欠測表記、前後空白、不正な数値、年・区画・調査回・処理区・Basic_Typeの範囲外を明示的に拒否する。文字列splitによるCSV解析、trim補正、欠測の0補完はしない。

`Year` は整数2014/2015、`Plot` は厳密検査後に文字列の元ID1〜24、`Round` は各年の元ラベルを文字列で保持する。2014は1,3,4,5,7,8,9、2015は1〜7。植物・昆虫名は綴り・大文字小文字・アンダースコアを含め原値を維持し、`plant:<raw>` / `visitor:<raw>` は原ラベル識別子とする。辞書の確認用フラグは同定や正規名の承認ではない。

`source_record_number` はヘッダーを除く1始まりのCSV論理レコード番号。対象原本には引用内改行がなく、物理行は番号+1で対応するが、契約は論理レコード番号。`record_id` は `sha256:<元SHA-256>:record:<番号>`。全3,882行を原順で保持し、同値行にも別の番号とIDを付ける。全7列を原行と1対1でテストする。原順を観測時系列とは呼ばない。

区画年IDは `<year>:plot:<plot>`、観測グループIDは `<year>:plot:<plot>:round:<round>`。グループIDは実施済みセッションの追加証明ではない。`observed_at`、`actual_effort_minutes`、`block_id` は必ずnull。補助CSVを結合しない。

## 監査と失敗の扱い

原CSVのハッシュ検証後、全件数・年別・年×処理・年×区画・年×回・年×区画×回、全原ラベルの年別件数・Basic_Type・確認用フラグ、7列同値パターン、欠測・分類/処理区の矛盾、15組の行なしを第3工程 `profile.json` と照合する。どれか違えば `AUDIT_MISMATCH` 等で停止。ヘッダーを件数に含めない。

全3,882件、年別1,687/2,195、植物20・昆虫104原ラベル、257観測ペア、48区画年、321記録ありグループ。7列同値は708グループ、削除した場合に失う1,930行を保持する。15組は `no_record_effort_unknown` として品質ファイルに記録し、イベントを追加しない。

`DataValidationError` は段階を示すコードと原因を持つ。CSVの値エラーには原論理レコード番号・列名を含める。別ハッシュの入力に対する製品用処理は、CSVを解析する前に失敗する。構文・型の負例テストは下位パーサーを直接呼び、ハッシュ検査が先に働くこととは分けて検証する。

## 決定性とコード履歴

JSONはUTF-8・LF・2スペース字下げ・末尾LF。プロパティの挿入順をコードで固定し、イベント配列は原順、辞書と集計は数値/コードポイント順を明示し、ロケール順や現在時刻を使わない。出力のハッシュはそのファイル自身へ埋め込まない。取得時刻は `source.json` と来歴だけに保持し、正規化の再実行では更新しない。

`CODE_INPUTS` に変換コード、固定契約・型・実行時検査、依存ロック、phase3のmanifest/profileを列挙する。それらに最後に変更を加えた**実在するGitコミット**を記録し、そのコミット内の各ファイルと現在のバイト列が一致することを確認する。各ファイルのSHA-256も残す。存在しない将来コミットや工程3のコミットを工程4の変換コードと偽って記載しない。

変換の変更時は、コードと依存・契約を先に作業ブランチへコミットし、`data:normalize` で来歴付き成果物を作成して次のコミットへ保存する。後者が出力・説明文だけの変更なら、変換コミットは前者のまま。最初の導入でもコードを保存後、正式な正規化コマンドで来歴を確定する。未コミットの変換変更や履歴不足は失敗し、成果物を更新しない。

## アプリ用の利用入口

後工程は `src/features/data/index.ts` の `loadObservationData(): Promise<ObservationData>` を使用する。3ファイルを遅延importし、Web Cryptoでイベント・辞書のUTF-8バイト数とSHA-256を照合してから、出典・版・型・全レコード番号・ID・年別ラベル集計・辞書との対応・nullを実行時検査する。成功後はネストを含めfreezeし、readonly型として返す。型アサーションだけでJSONを信用しない。取得失敗を空配列へ変換しない。ハッシュの根拠は同じGitコミットに保存したmanifestであり、外部からの電子署名検証を行うものではない。

今回は画面から呼ばず、実データは既存画面のJavaScriptへ取り込まれない。後から画面へ接続する工程で、出典・英国実験・原ラベル・訪花と受粉成功の区別を表示し、idle/errorと有効な結果を分ける。
