# ECO MIRROR 3.0｜第4工程・地図上の「自然の橋」研究仕様 v0.1

**対象：第1〜3工程で取得したESA WorldCover 2021 v200の東京2km×2kmの土地被覆図。** 本工程は「実際に施工可能な場所を見つける」「ハナバチの移動改善を実証する」工程ではなく、**地図の仮想セル変更によって構造的接続性が変わるか**を比較する研究実験。

## 1. 何を改善の候補とするか

- 地図格子は10m解像度。1か所あたり2×2画素、合計4画素＝**400m²**を一律に植生候補として変更する。
- 候補は**元のESA分類コードが50（Built-up）または60（Bare / sparse vegetation）のみ**。80（水域）、既存植生、未確認画素は禁止。元分類を保持してSHA256を検証する。
- **これは建築物や民有地の緑化を勧めるものではない**。ESAのbuilt-upは「工事できる空地」という意味ではない。所有権、法令、環境影響、施工性は未確認。
- 同じ追加面積と同じ440条件で、各候補の改善前・改善後を再計算する。条件ごとに削減した元植生の操作は完全に同一のキャッシュから共有し、追加地点だけを変える。

## 2. 候補地の列挙・選択（網羅性を明示）

- 2kmの地図上で**格子x,yとも偶数**の2×2画素を、外周から8画素内側に限定し、元分類が50/60のものを全走査する。
- 元の植生候補パッチが**4近傍で連結しているか**を調べる。3画素以上からなる別々の植生候補パッチが、半径5画素の周囲に2つ以上あれば**「潜在的な接続候補」**とする。この3画素・5画素は**発見のための仮の空間ヒューリスティック**であり、生物学的に実測された分散距離ではない。
- 近くに2つ未満の地点から、同じ400m²の**比較対象**を選ぶ。
- 候補の近さ・近隣パッチ数に加えて「実際に2つ以上のパッチを1つに結ぶか（4/8近傍）」を優先し、地図を5×5区域に分けて**区域ごとに最大1か所**を選ぶ。最初の研究では**接続候補最大12か所＋比較対象最大4か所**だけを実際に計算する。
- **すべての潜在的な候補地点でシミュレーションしたわけではない。** この手法を地域全体の「真の最適地」「施工できる最良地点」と呼ばない。候補選択範囲と件数は全て保存する。

## 3. 「本当に緑地をつなぐ」かを区別

候補地点の追加前に地図を4近傍と8近傍の2通りでパッチ分割する。追加2×2画素に**接する異なる元パッチが少なくとも2つ**あり、追加によって元パッチ同士が結合する条件を確認する。

- **両ルールでパッチが結合**：直接の地図上の橋（最も強い構造的ラベル）
- **片方だけで結合**：連結方法に依存する橋
- **どちらでも結合しない**：踏み石候補・既存パッチの延長・孤立した新規パッチ
- **それでも実際の生物が移動できる証拠にはならない。** 分類誤差・道路・障壁・花資源・季節・生物ごとの移動能力を考慮できていない。

## 4. 同じ440条件で比較

直前の第2工程と**完全に同じ条件**を使用し、計算前後でPC指標を比較する。

- λの仮説値10種類：40,60,90,135,200,300,450,675,1000,1500m
- 仮想の植生除去率11種類：0,5,10,15,20,25,30,35,40,45,50%
- 4/8近傍：2種類
- 除去パターン：distributed/edge_firstの2種類
- 合計 **10×11×2×2=440**。候補12か所なら**12×440**、同面積対照4か所なら**4×440**を計算する。

候補a・条件sでの効果は、同一地域面積と同一条件で計算した

\[
\Delta PC_{a,s}=PC_{a,s}^{after}-PC_s^{before}.
\]

すべてのΔPCを符号を含めて記録。平均だけでなく**最低値、下側10%点、中央値、最大値、正・負・ゼロの条件数**を表示する。

\[
a^*=\arg\max_{a\in\mathcal A_{\rm selected}}
Q_{0.10}\left(\{\Delta PC_{a,s}:s\in\mathcal S_{440}\}\right).
\]

これは対象候補の**仮定の全条件における下側10%点を最大化**する研究上の選択法であり、**確率分布でも最適施工候補でもない**。格子選択ルール・λ・減少パターンを変更したら結論も再評価する。

## 5. 独立した検証方法

1. 2021の公式土地被覆コード原画素から植生マスクへ変換した結果と派生SHA256を検証。元の巨大COGタイルの完全ハッシュと混同しない。
2. 2×2の4画素が全て元分類50/60で、重複せず、端の8画素余白も守ることを確認。
3. 全候補ごとに**440件すべて**があることを確認。途中失敗した場合の欠落した条件を黙って除去しない。
4. 全数の改善前PCと第2工程の正式結果を照合。改善後の植生面積が**毎条件ぴったり400m²**増えることを確認。
5. Pythonの独立計算で、低分位点と候補順位、正・負・ゼロの件数をクロスチェック。
6. Pythonで独立に4/8近傍のパッチを連結し直し、真にパッチを結ぶと表示している地点が**両方式でパッチ数を減らす**ことを検証。
7. 一部の条件について、**Pythonで独立実装したPC式を最初から計算**し、TypeScriptの改善前後の値と数値一致させる。
8. 既存の元データ、イベント抽出数理、正式RunResult、PCG32系列、通常画面のテストとビルドを続け、影響がないことを検証。

## 6. 結果の科学的な意味

- **計算可能**：同じ2021の地図に仮の植生追加を施すと、構造的PCがどう変わるか。
- **未検証**：本当にハナバチの生息・移動・授粉・繁殖が改善するか、施工できるか、2026年に土地分類が同じか。
- **未実装**：実際の空間抵抗地図、合法的に緑化可能な地番・土地利用の照合、対象の分散距離の外部校正、2km外側バッファ、複数地域の外部検証。
- **限界**：全候補ではなく、あらかじめ決めた基準で抽出した有限の地理的ショートリストを評価。モデルが下側10%の指標で優れることは、現実世界で保全優先度が高いことを意味しない。

## 7. 必要な再現手順

1. Phase 1–3と同じESA COGの窓を取得（Pythonのrasterioとpyproj、numpy。バージョンはワークフローに固定）。
2. Phase 1–3の440条件を再計算し、元結果のSHA256と同一であることを確認。
3. Phase 4で元分類コードとハッシュを照合し、候補を全列挙→地理的ショートリスト→全440条件×全選出地点を実行。
4. Python独立監査を全てPASSさせる。
5. 数値・結果JSON・コード版・CI実行ログ・科学上の限界を、PR内の検証結果とartifactとして記録する。
