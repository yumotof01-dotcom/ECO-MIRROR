# 観測モデル仕様 1.0.0

本書は数理仕様。抽出コード・エンジンはまだ作成しない。関連する指標、乱数、反復、結果形式は[仕様一覧](README.md)の各文書を規範とする。「必須」「禁止」は後工程の実装条件を示す。

## 1. 推定対象と固定入力

問いは「選択範囲の全訪花記録で確認できる原ラベル間の関係が、記録を一部残すとどれほど確認できなくなるか」。自然界の未観測関係、受粉成功、個体数減少、時間短縮はモデル化しない。

工程4の `loadObservationData(): Promise<ObservationData>` から得た検証済み・readonlyデータを使う。対象IDは `moss-evans-2022-flower-visits-v1`、原CSVのSHA-256は `c2d7023215fb885070caf6603886bce10e965732e3cc2465111e9d73cad9ab9a`、正規化 `events.json` は `17c87b30f3f66f8d3537123c75ea29a8d3193f9f1f0381a8e48460fd3f73d58c`。全3,882記録を母ファイルとする。

| 既存フィールド | このモデルでの役割 |
| --- | --- |
| `dataset.dataset_id / source_sha256 / schema_version / transform_version` | ファイル全体の出典・版。イベント個別への複製は不要 |
| `dataset.events` | 元レコード番号の昇順。配列・各要素を変更しない |
| `record_id / source_record_number` | 行の識別と追跡。同値行も別々の抽出単位 |
| `year / plot_id / treatment / round_label` | 選択範囲の条件 |
| `plot_year_id / observation_group_id` | 記述上の区画年・年区画回のキー。独立性・実施済みの証明ではない |
| `plant_label_id / visitor_label_id` | 植物と昆虫を分けた原ラベルのノードID |
| `plant_label_raw / visitor_label_raw / basic_type_raw` | 原表記・著者の分類。名寄せや機能群の再推定をしない |
| `observed_at / actual_effort_minutes / block_id` | nullを維持。抽出条件にしない |
| `taxa.plants / taxa.visitors` | ファイル全体の辞書。選択範囲のノード数の分母へ無条件に使わない |

全ファイルを検証してから選択する。部分抽出後の配列を既存の `validateObservationData` に再入力しない。この関数は全3,882件を検証する契約であり、変更して部分データを通す必要はない。派生スコープと結果は、後工程で別の型・純粋関数として定義する。

結果の出典・コード版を組み立てる呼出側は、既存の `artifacts.json` と `provenance.json`、固定契約、実在する計算コミットと規範文書ハッシュからreadonlyの実行コンテキストを別途用意する。計算コアへ値として渡し、コア内でファイル・Git・通信を読まない。既存のObservationDataやローダーに来歴フィールドを追加するための改変は不要。実装コードを先にコミットし、そのコミットを参照する来歴を後から保存する工程4の方法を利用できる。

## 2. 選択範囲

選択入力 `selection` は次の4項目をすべて必須とする。暗黙の「全て」や、空配列を全選択とする規則は設けない。全選択時は全ての値を明示的に列挙する。

| 項目 | 型・許容値 | 正規順 |
| --- | --- | --- |
| `years` | 2014/2015の非空配列 | 年の数値昇順 |
| `plot_ids` | 元文字列 `"1"`〜`"24"` の非空配列 | 区画番号の数値昇順 |
| `treatments` | `Control`, `Heat`, `Heat+Water`, `Water` の非空配列 | この表記の順（ASCII順） |
| `rounds_by_year` | 選択年をキーとするオブジェクト。各値は非空の元Round文字列配列 | 年の昇順、各年内は番号の数値昇順 |

2014の許容Roundは `"1","3","4","5","7","8","9"`、2015は `"1","2","3","4","5","6","7"`。キーは選択年と完全一致させる。未選択年のキー、欠けた年、未知の項目・値、重複値、空配列、数値型のPlot/Round、`"01"`、空白付きの値は `INVALID_SELECTION`。補正や無言の無視はしない。配列の入力順だけは意味を持たず、上記の順へ正規化する。

将来の選択UIの既定値は両年・全24区画・全4処理・各年の全許容Round、p=50、seed=42。反復モードの既定Rは100、単一モードはR=1。APIにはこの既定値を明示して渡し、省略から補完しない。今回既存フォームへ選択UIを追加しない。

年・区画・処理・Roundは**項目間AND、同じ項目内OR**。イベントeが次をすべて満たす場合だけ残す。

$$
e.year\in Y,\quad e.plot\_id\in Q,\quad e.treatment\in T,
\quad e.round\_label\in R_{e.year}.
$$

順序を保つfilterの結果を $D=(e_1,\ldots,e_N)$ とし、これをこの実行の**比較基準**とする。アプリ全3,882件を常に分母にするのではない。原同値行の削除、分類フィルター、重みの変更、処理区の再割当は行わない。

選択範囲の表示には年・区画・処理・年別Roundと、N、記録のある区画年/グループ数を必ず含める。年別の実際の記録数も記録する。両年選択時は `scope_mode = "pooled_records"`、片年時は `"single_year_records"` とする。二年間をまとめた同一ラベルのペアは同じペアとして数えるが、年別のペア数の和を全体のペア数にしない。

### 処理・年・区画を分ける際の制約

- Treatmentは各Plotに付与された元属性。元記録を条件で絞るだけで、未記録の処理×区画を生成しない。
- 全3,882件をまとめて抽出した場合は一つのプールである。**年別・区画別・回別の件数や割合を固定する層化抽出を行わない。** 記録の多いグループはイベント数に応じて多く含まれやすい。
- 2014/2015のRoundを共通の時系列や等間隔へ変換しない。両年のRound 1が同日・同季節段階だったとは仮定しない。年を無視してRoundを結合する選択APIを置かない。
- 48の年×Plotは記述用の分割単位。同じPlot IDが両年に現れ、処理は同じで、論文はブロック設計を記す。IDの一致だけから物理的な区画の継続性や年をまたぐ依存構造まで確定しない。CSVにブロック情報がないため、48の独立した実験反復として検定・信頼区間・処理効果推定へ使わない。イベント3,882件も独立した生態学的反復ではない。
- 年・区画・処理を分けた比較は、それぞれの全記録に条件付けた記述。標本サイズ・原頻度・分類構成も違うため、同じ割合の保持率だけで処理や地域の優劣を結論しない。

構文上正しい条件でも、PlotとTreatmentが交わらない、又は選択したグループに行がない場合はN=0になり得る。結果は `empty_scope` とし、試行しない。行なしグループは `no_record_effort_unknown` のまま保持する。[境界条件](edge-cases.md)を参照。

## 3. 抽出単位と選択理由

MVPは各正規化イベントを1単位とする、**非復元・固定件数の単純無作為抽出**。Dの各記録には異なる原レコード番号があり、内容が同じでも別の対象となる。

| 候補 | MVPの判断 |
| --- | --- |
| 個々のイベント、固定件数、非復元 | 採用。指定した記録数を確実に残せ、全原行と対応できる |
| イベントの独立Bernoulli抽出 | 今回不採用。割合を指定しても残る件数が変動し、固定件数モデルとは異なる |
| 復元抽出（bootstrap） | 今回不採用。同じ原行を重ねて選ぶため、残す記録の部分集合にならない |
| 回・区画をまとめて抽出 | 後の別モデル。調査内のまとまりを保てるが、実施状態不明・不均衡と抽出件数の別設計が必要 |
| 異なるペアを等確率で抽出 | 不採用。原頻度を捨て、希少なペアも頻出ペアも同確率になる |

イベント間の独立性は実験デザインの事実として主張しない。数学上の無作為選択を定義するだけで、現実の観測者・時間・採集機会の偏りを再現するものではない。

## 4. 割合から件数への変換

指定割合pは**整数0〜100（単位%）**。不正型、小数、NaN、Infinity、範囲外は `INVALID_RATE`。Nは選択後の行数で、0〜3,882。

$$
k=\left\lfloor\frac{Np+50}{100}\right\rfloor,
\quad p_{\mathrm{realized}}=100\frac{k}{N}\quad(N>0).
$$

最近整数への丸めで、ちょうど0.5件なら上へ丸める。最低1件の強制、ceil/floorへの切替、確率的丸め、グループごとの丸めはしない。`N*p+50` は最大388,250であり、JavaScriptの安全な整数範囲内。途中で `p/100` の浮動小数にして丸め方を推測しない。指定pと実現割合を別々に保存・表示する。

N=0をこの算術式だけに与えるとk=0だが、実行APIはそれより前に `empty_scope` を返す。その実行の `sample_record_count` はnullであり、0件を抽出した成功とは区別する。fixtureのN=0の丸め例は算術式だけの期待値。

| N | p | k |
| --- | --- | --- |
| 100 | 50 | 50 |
| 3,882 | 50 | 1,941 |
| 1,687 | 50 | 844 |
| 2,195 | 50 | 1,098 |
| 1 | 49 / 50 | 0 / 1 |
| 3 | 50 | 2 |
| 7 | 99 | 7 |

年別に丸めた844+1,098=1,942と、両年プールの1,941は異なるモデルなので一致を要求しない。小標本では0%以外でも0件、100%未満でも全件になり得る。pを時間や実地の検出確率へ変換しない。

将来のUIは0%を選べる設計とする。これは正の比較基準に対する有効な空抽出を明示し、境界を検証できるため。現行の未接続フォームの1〜100はこの工程で変更しない。

## 5. 抽出アルゴリズムの規範

次は実装用の手順定義であり、実行コードではない。乱数・棄却法は[randomness.md](randomness.md)に従う。添字は0始まり。

1. 入力・データを検証しDとNを確定する。N=0なら `empty_scope` を返し、乱数生成器を作らない。
2. kを計算する。k=0なら空配列、k=NならD全件の原番号配列を返す。いずれも乱数を消費せず、原本は変更しない。
3. 0<k<Nなら、この試行のシード組で新しいPCG32を初期化する。
4. 作業配列 $I=[0,1,\ldots,N-1]$ を作る。元イベント配列をシャッフルしない。
5. i=0,1,...,k−1の順に、$b=\operatorname{boundedUint}(N-i)$、j=i+bとし、I[i]とI[j]を交換する。j=iの自己交換も省略によって乱数系列を変えない。
6. Iの先頭k個が採用された位置。結果の保存・集計前に、採用位置を**数値昇順**に整列し、Dの順序の部分列Sを得る。選択に用いた交換順と保存順を混同しない。
7. Sの原番号・record_idを保存する。異なるNやフィルターに同じシードを使っても、同じ原番号が選ばれる保証はない。

理想的な一様整数列の下では、各順列の選択済みprefixは確率 $1/[N(N-1)\cdots(N-k+1)]$。各k部分集合にはk!個の順が対応するため、

$$
\Pr(S=s)=\binom Nk^{-1},\quad
\Pr(e\in S)=k/N,\quad
\Pr(e_a,e_b\in S)=k(k-1)/[N(N-1)]\ (N>1).
$$

したがって同一試行内の採用指示は独立Bernoulliではない。PRNGはこの理想モデルを決定的に実現するための数値手段であり、有限のシード集合が全部分集合を厳密に等頻度で覆うとは主張しない。

同一D・シード組でpを変えると部分Fisher–Yatesのprefixを共有し、kの小さい標本は大きい標本の部分集合になる。0/全件の特例もこの包含関係を満たす。将来割合曲線を作る場合、この対応付き設計を記録し、割合間を独立試行と呼ばない。今回曲線や実行コードは作らない。

## 6. 後工程の関数境界

| 工程6で実装する責務 | 入出力契約 |
| --- | --- |
| 条件検証・正規化 | selectionを検査し、規定順・重複なしの新オブジェクトへ変換 |
| スコープ準備 | 検証済みObservationData→原順の参照と原番号の集合、参照ネットワーク。N=0は別状態 |
| 件数計算 | N・整数p→一意のk、指定割合と実現割合 |
| 乱数生成・整数範囲化 | この仕様のPCG32と棄却法。グローバル状態なし |
| 単一試行 | 準備済みスコープ・p・master_seed・trial_index→Sの原番号、指標、乱数語消費数 |
| ネットワーク集計 | D・S→原ラベルのペア重み、相手数、固定分母の指標 |

いずれもReact/DOM・時計・通信に依存しない純粋な計算契約。乱数状態は試行ごとに所有し、入力配列を変更しない。合成fixtureは下位関数のテスト専用で、全ファイル検証ローダーの採用データへ混ぜない。反復ループは工程7まで実装しない。
